# Live Scavenger Hunt app API contract

This is the contract for `app/`. All times are UTC ISO strings or epoch milliseconds from the server. Every route is event-scoped by immutable slug. All JSON errors have `{ "error": "...", "code": "..." }` and an appropriate HTTP status. A stale event revision returns `409` with the latest revision.

## Browser routes

`/e/:slug/arena`, `/e/:slug/play`, `/e/:slug/vote`, `/e/:slug/operator`, `/e/:slug/metrics`, and `/login`. The operator and metrics pages may load publicly, but their data and actions require an authenticated session. `/` redirects to the seeded event arena. `GET /favicon.ico` serves a multi-size official Twilio bug icon; each page also links 16, 32, and 48 pixel PNG variants under `/assets/` with a versioned URL to refresh browser favicon caches. `GET /e/:slug/github?source=arena_qr|arena_link` records a source-tagged repository click and returns a no-store `302` to the fixed GitHub project URL; an unknown source is rejected. The arena accepts `?demo=hunt|vote|win|lose|tie|no-match` with an optional `players` value from 2 to 6; the phone accepts `?demo=win|lose|tie|no-match|decision|build`. These local visual previews do not join a heat, connect media, judge, collect leads, or write activity. Their outbound product and GitHub links still navigate; the arena's preview star link bypasses the tracked redirect.

## Public state

`GET /api/e/:slug` returns `{ event, state, serverTime }`. `GET /api/e/:slug/stream` sends initial and changed payloads in SSE `state` events, with keepalive comments. `event` contains public event name, player range, timing, `startMode`, `leadCapture` with `timing:"after-play"|"join"`, `cta.primary:"github"|"guide"|"expert"`, voting settings including `vote.autoCategory:boolean`, and media mode; it never contains the prompt deck or secrets. A missing legacy lead timing and CTA normalize to `after-play` and `github` for the public clients. Missing legacy `vote.autoCategory` normalizes to `false`. Admin event saves validate that guide or expert is enabled before it can become the primary CTA. Player and arena clients request a fresh snapshot at the countdown deadline if SSE is delayed; the sealed prompt remains hidden until the server responds with `phase:"hunt"`.

New events default to a 45-second hunt, a 15-second result hold, 60-second seeded creative prompts, and AI-assisted prompt judging. Their lead settings default to `timing:"after-play"`, `guideEnabled:false`, `expertEnabled:true`, and `cta.primary:"github"`; existing saved event lead settings are unchanged. New events and legacy events missing `vote.autoCategory` use `false`, so category ballots require a staff `openVote` command unless an admin opts in. One-time startup migrations apply the hunt and creative timer and AI defaults only to untouched revision-1 legacy events; they do not change saved result durations. Events already edited by an admin keep their saved timers and judging modes, even when those values match older defaults. The seeded deck now has 80 prompts; 30 new conference Pilot options start disabled. A separate one-time startup migration appends missing Pilot prompts to saved event decks without changing existing prompts or their order, limited by the 100-prompt event maximum. Any migration that changes an event increments its revision; active heat snapshots keep their locked rules.

`state` has `{ eventId, phase, heat, version, resultRevision, paused, roster, queuedCount, readyCount, lockedCount, readyDeadline, countdownEndsAt, roundEndsAt, resultEndsAt, prompt, winners, vote }`. `resultRevision` is a monotonic event-level count of operator result overrides and corrections; an open finished-player phone uses an increase to refresh the completed result it is still displaying. Each current-heat roster item is `{ id, alias, slot, status, mediaConnected }`; queued players appear only in the operator state `queue`, while public state exposes their count but no identities or positions. At heat lock, the server snapshots `{id,alias,slot}` for result display. A locked player who disconnects and times out remains in their original result tile with `mediaConnected:false`, but cannot submit a new winning evidence frame after disconnecting; an explicit leave before the result removes them from that result, and a kick always removes them. Leaving during the result keeps that celebration visible. `prompt` is omitted before GO, then `{ id, text, category, seconds, judgeMode }`. `winners` is an array of player IDs for the current result. Corrections to an earlier heat are retrieved through the authenticated player's `completedResult`, not published in `state.winners`. `vote` is absent unless a vote window exists; when present it has `{ id, type, status, closesAt, options, tallies, result }` and never reveals phone numbers. Wall and player clients compute countdowns from server deadlines and `serverTime`. In `flexible` and `deadline` start modes, `readyDeadline` is `null` until at least `event.minPlayers` are ready. It becomes `now + event.joinSeconds` when that minimum is reached, clears if the ready count falls below the minimum, and is reset from the current time if the relevant event settings change. During a pause, public deadlines are `null`; the operator state holds remaining time in `pauseRemaining`, including a join window opened by newly ready players or an open vote started during the pause. An open vote has `closesAt:null` while paused; its full or remaining window resumes afterward. `flexible` also locks immediately when `event.maxPlayers` are ready; `capacity` waits for the maximum and `manual` waits for an operator. New events default to `manual`; saved events keep their configured mode. A full `flexible` or `capacity` lobby reached during a pause locks on resume if no vote is open. The arena displays `readyCount` as a plain count, not as a fraction of capacity. Replay-slot claim deadlines are private runtime data, not part of public `state`.

`GET /api/e/:slug/qr.svg?target=play|vote|github` returns a real SVG QR. Play and vote targets encode the event's absolute HTTPS/public URL (local development may use localhost). The arena keeps the play target visible in every phase; an open, unpaused ballot displays a separate smaller vote target. The live GitHub target encodes the event-scoped tracked redirect with `source=arena_qr`; `target=github&preview=1` encodes the fixed GitHub repository directly so a visual preview does not write activity. `/api/e/:slug/frame/:playerId` requires an authenticated operator session and serves only the latest transient rehearsal/evidence JPEG for a visible player; no frames are saved to the database. The signed-in wall can use this endpoint to fill a missing result-frame snapshot, then holds that image only in wall-browser memory through the result.

## Player and spectator actions

| Route | Input | Response |
| --- | --- | --- |
| `POST /api/e/:slug/join` | `{alias,displayConsent:true,lead?:{fieldValues:{[fieldId]:string}}}` after display and image-review consent | HTTP `201` with `{player:{id,alias,slot,status,heat,queuePosition},token,state}`. `lead` is required only when lead capture is enabled **and** its timing is `join`; then the player and one `intent:"capture"` lead are saved atomically. For `after-play` or disabled capture, contact fields are not required. The phone checks camera access before calling this route; the API still validates consent and event rules. An enabled event can also accept optional valid contact fields at join. A full or locked heat queues the visitor. Existing queued visitors take any open lobby spots before newer joins. New `marketingOptIn:true` submissions are rejected when lead fields are captured; legacy `false` is accepted. |
| `GET /api/e/:slug/me` | `Authorization: Bearer <player token>` | `{player,state}`, including the caller's private one-based `player.queuePosition` when queued, or `null` otherwise. A finished player's `completedResult` is `{heat,winners,winnerNames}` for their latest completed heat at or before `player.heat` whose saved locked roster includes them, excluding a heat they explicitly left after lock but before its result. A voluntary leave during the result keeps that heat eligible. It is `null` when no eligible result exists. The saved roster and leave timing identify the result, so a replay timeout can advance `player.heat` without changing the last competed result; `winners` contains player IDs and `winnerNames` contains corresponding public screen names. Valid `finished` and `left` sessions can be read for seven days from their latest join; active player actions keep a 24-hour token window. A kicked session still receives `403`. The private player includes `needsJoinLead:boolean` for a finished/left player with no capture lead when current event settings require At join, plus nullable `lastExitReason` when the session last exited. A replay claim timeout sets `lastExitReason:"replay_timeout"`. |
| `POST /api/e/:slug/ready` | Player bearer token | `{player,state}`; requires media ready or explicit rehearsal mode. A player with a lobby slot can become ready while the booth is paused; this does not start a heat or spend join-window time until resume. A player queued during a paused active heat cannot mark ready until promoted into a lobby slot. |
| `POST /api/e/:slug/replay` | Finished or left player bearer token; optional `{lead:{fieldValues:{[fieldId]:string}}}` | `{player,state}`; keeps the same player ID, token, alias, and existing captured lead. It takes an available lobby slot after earlier queued visitors or joins the waitlist with a private `queuePosition`. If At join was enabled after an earlier no-lead join, `player.needsJoinLead` is true and replay requires the current contact form: a missing lead returns `409` `join_lead_required`; valid fields save one capture lead atomically, and invalid or changed fields use `invalid_lead` or `lead_form_changed`. A supplied lead is ignored when already captured or no longer required. An active player gets `409` `replay_unavailable` until they finish or explicitly leave. A player who leaves during countdown, hunt, or review can replay immediately into the next-heat queue; GO and finalization of the old heat do not reactivate or finish them. Repeated calls while already joined, ready, or queued are idempotent. A returning player promoted into an active lobby slot has 30 seconds of active lobby time to reconnect and become ready; on expiry the server releases the slot, returns that player to `finished` with `lastExitReason:"replay_timeout"`, and records `player_timed_out`. A booth pause freezes that 30-second window. The timed-out player stays `finished` when later heats lock and is not silently requeued. The same token can call `/replay` again after expiry. More than eight replay calls per token in 60 seconds return `429` `rate_limited` with `Retry-After`. |
| `POST /api/e/:slug/heartbeat` | Player bearer token | `{player,state}` with refreshed private `queuePosition` and the same `player.completedResult` shape as `/me` when the player is finished. The player page sends this about every five seconds while open. |
| `POST /api/e/:slug/leave` | Player bearer token | `{state}`; marks the session left and releases the slot. In a lobby, the oldest queued visitor takes the vacancy. The player page also stops its local camera. |
| `GET /api/e/:slug/media-token` | Player bearer token | `{mode,token?,roomName?,identity?}`. Twilio tokens are room-scoped. |
| `POST /api/e/:slug/frame` | Player bearer token, `image/jpeg` body, max 150 KB | `{ok:true}`; rehearsal frames and the phone's downscaled, uncropped browser frame for judging, rate-limited. Phone evidence gets the first 2.5 seconds after GO and remains preferred while fresh; authenticated wall evidence may judge if phone frames are missing or stale. A live Twilio player whose signed Video callback marks their media disconnected receives HTTP `409`, `code:"media_required"`; the server will not store that frame for judging. |
| `POST /api/e/:slug/votes` | `{windowId,choice}`; anonymous voter cookie | `{accepted:true,vote}` or `409` duplicate/closed. An open ballot paused by staff returns `409` with `code:"vote_closed"` until resumed; its vote window is preserved. A vote never creates a lead. |
| `POST /api/e/:slug/leads` | Player bearer token, `{intent:"guide"|"expert",fieldValues?:{[fieldId]:string}}` | HTTP `201` with `{leadId,deliveryStatus}`. An at-join lead is marked with the requested follow-up without asking again. An after-play player voluntarily submits configured fields on the first request, creating a lead with a field snapshot. A later compatible guide/expert request can omit `fieldValues` to reuse those details; a guide still needs an email. Repeating the same request is idempotent. A guide requested for the same event and email within 24 hours is saved with `deliveryStatus:"recent-request"` and does not create another email job. Finished players may submit after the arena advances to a later heat while their player token remains valid. New `marketingOptIn:true` submissions are rejected; legacy `false` is accepted. |
| `POST /api/e/:slug/spectator-leads` | Anonymous browser cookie, `{intent:"guide"|"expert",fieldValues:{[fieldId]:string}}` | HTTP `201` with `{leadId,deliveryStatus}`. The spectator form is voluntary and needs no player token; it is rate limited and identical submissions are deduplicated by browser session, intent, contact, and form answers within a day. Guide email also has a 24-hour per-event recipient cooldown independent of the browser cookie. Voting alone never creates a lead. New `marketingOptIn:true` submissions are rejected; legacy `false` is accepted. |
| `POST /api/e/:slug/activity` | `{type}` from an allowlist. `twilio_product_link_opened` also requires `product:"video"|"messaging"|"segment"`; `github_cta_opened` may include `source:"phone"|"spectator"`. The arena referral route sets its own source. | `{ok:true}`. Contact fields are rejected. |

Guide and expert submissions require the event's respective `leadCapture.guideEnabled` or `expertEnabled` option; a disabled follow-up returns `code:"lead_disabled"`. When guide requests remain enabled but server `SENDGRID_EMAIL_ENABLED` is unset or `0`, a new guide response has `deliveryStatus:"pending-configuration"`; its durable job is `waiting-config` and no Mail Send call is made. Lead capture and expert follow-up continue. Saved `waiting-config` jobs may send automatically after the server restarts with `SENDGRID_EMAIL_ENABLED=1` and a valid API key and From address, so admins should review old requests before re-enabling. The event **Build guide** option can be turned off separately to stop new guide requests.

The server orders queued players by join time and insertion order. Leave, operator removal, presence timeout, and a capacity increase fill open lobby slots from the queue before any later join; the next heat takes up to the configured maximum in the same order. Only the caller receives `queuePosition` through authenticated player responses; public state exposes `queuedCount`. The phone estimates heats away as the ceiling of position divided by maximum players. It does not report a minute ETA because operator timing, votes, and pauses vary.

At-join capture records `lead_captured`; later player and spectator guide/expert actions record `lead_submitted`. The default At join fields and display/image consent fit together on one phone form; longer custom fields paginate. A spectator ballot does not use the join form and never creates a lead. Captured contact values are excluded from public state and activity payloads. The player page stores the opaque event-scoped token and short camera-tab lease in browser storage but no raw lead field values. A same-origin, same-profile QR rescan reads `/me` and restores active or queued play, the finished decision, or a left-session rejoin. Replay turns off the camera between heats and records another `player_joined` entry under the same player ID; `player_joined`, `player_queued`, and voluntary `player_left` are counted at most once per player per heat. An explicit leave by a locked player during countdown, hunt, or review also emits the internal `player_result_opted_out` activity, even when a lobby leave already used that heat's `player_left` count. The opt-out excludes that heat from a later `completedResult` lookup and does not add another `playerLeaves` report count; it is server-generated, not accepted by `POST /api/e/:slug/activity`. A leave during the result does not emit an opt-out. The completed heat's result roster remains visible through its hold, including players who disconnected and timed out mid-heat. No choice on the post-result decision creates a new lobby claim or queue entry. After an operator removes a player, that token receives HTTP `403` with `code: "player_kicked"` on authenticated player routes. The phone turns off its camera and shows a removal screen. Missing or expired player tokens receive `401`. A valid left token can call `/me` and `/replay` but not heartbeat, media, or other player actions until replayed. The server also marks stale sessions left when heartbeats stop: about 25 seconds for waiting/queued players and 60 seconds during a heat.

## Authentication and operator actions

`POST /api/auth/login` takes `{username,password}` and sets an HttpOnly SameSite session cookie. `GET /api/auth/session` returns `{user:{id,username,role,authProvider},csrfToken}`. Admin/operator mutations require `X-CSRF-Token`; `POST /api/auth/logout` ends the session. Admin can configure events and view leads; operator can run heats and review candidates. A first run with no users prints a generated one-time admin password to the server terminal, unless `BOOTSTRAP_ADMIN_PASSWORD` was supplied. That bootstrap setting does not reset existing accounts.

`GET /api/auth/providers` is public and returns `{google:{enabled:boolean}}`. Google is enabled only when `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` are both present with the canonical `PUBLIC_BASE_URL`. `GET /api/auth/google/start?next=...` begins an authorization-code flow with PKCE, nonce, and one-time state; it redirects to Google when configured. `GET /api/auth/google/callback` validates that state and Google's signed ID token, sets the same staff session cookie, then redirects to a safe same-origin `next` path. A failed sign-in returns to `/login` with a short error code. The server requires a verified `@twilio.com` email and `hd=twilio.com` in the token. It keys identity by Google's stable `sub` and grants **admin** access on verified sign-in, including Team, Metrics, and leads. An existing Google operator is upgraded only on a new verified sign-in; stored email alone does not grant access. The `hd` authorization parameter is a hint, not the access check.

`POST /api/auth/password` takes `{currentPassword,newPassword}` for the signed-in local-password user and requires CSRF. It ends every session for that account, clears the current cookie, and requires a fresh sign-in. `POST /api/auth/username` takes `{currentPassword,username}` for a signed-in local-password user and also requires CSRF. It normalizes the new username to lowercase, returns `{user}`, revokes every session, clears the cookie, and requires sign-in with the new name. Usernames must start with a letter and contain 3–80 letters, numbers, dots, dashes, or underscores. Duplicate names return HTTP `409`; an incorrect current password returns `403`. Google names remain managed by Google. An admin can edit the existing primary local admin account or manage separate operator accounts through these global routes:

| Route | Role | Input / output |
| --- | --- | --- |
| `GET /api/admin/local-admin` | admin | `{admin:{id,username,role,authProvider}}`; returns the oldest local password admin account, which remains the same row after a rename. |
| `POST /api/admin/local-admin` | admin + CSRF | `{username,password?,expectedUsername?}` → `{admin,usernameChanged,passwordChanged,signedOut}`; updates that existing account atomically. Keep `username` unchanged and send a new `password` to reset it; omit `password` for a rename only. The Team editor sends `expectedUsername` from its last loaded record; if another admin renamed the account, the request returns `409` with `code: "admin_changed"` before changing it. Revokes that account's sessions; a local caller editing itself is signed out, while a Google admin caller stays signed in. No password is returned or audited. Duplicate usernames return `409`; a request with no change returns `400`. |
| `GET /api/admin/operators` | admin | `{operators:[{id,username,role,authProvider,email,createdAt}]}`; returns role=`operator` accounts. Legacy Google operators may appear until their next verified sign-in; Google admins are not listed. |
| `POST /api/admin/operators` | admin + CSRF | `{username,password}` → `{operator}` with HTTP `201`; creates an `operator` only. |
| `POST /api/admin/operators/:id/password` | admin + CSRF | `{password}` → `{operator}`; resets a local operator's password and revokes their sessions. |
| `POST /api/admin/operators/:id/username` | admin + CSRF | `{username}` → `{operator}`; renames a local operator and revokes their sessions. Admin IDs return `404`; legacy Google operator IDs return `409`. |
| `DELETE /api/admin/operators/:id` | admin + CSRF | HTTP `204`; removes a local operator and revokes their sessions. |

Local usernames are normalized to lowercase and must be 3–80 characters using letters, digits, dots, dashes, or underscores, starting with a letter. Local passwords have no minimum length or character rule; the only size ceiling is 16,384 UTF-8 bytes so even two heavily escaped passwords fit within the 240 KB auth JSON request limit. These account routes reject role elevation and Google-account password operations. `scripts/create-user.mjs` remains available for a stopped local database; the hosted container does not include that recovery script.

The operator state also includes a five-heat `recentHeats` list with prompt, player IDs, and winners so an operator can correct a completed result after advancing the arena. `judgeNotice` is visible only in operator state, never on the public arena or player state. While it is set for an AI-assisted heat, `reviewEndsAt` stays `null`; an operator command completes the heat.

`kickPlayer` takes `payload: {playerId}` for a current-heat or queued player. It clears the slot, invalidates the token, records `player_kicked`, and removes that player from candidates and creative ballots. If the player had already won the displayed result, the stored winner list is corrected. Its response adds `mediaDisconnect: {status:"ok",mode,disconnected}` on a successful Twilio disconnect attempt or `{status:"failed"}` if the media operation fails; the player is removed from the game in either case.

The private report summary includes `joinSessions` and `totalParticipants`, both counting entries including replay; `uniquePlayers` deduplicates by player ID. `uniqueVisitorSessions` counts distinct browser sessions where IDs exist, while `unattributedJoinSessions` counts older joins without one. Browser sessions are a device/browser measure, not verified unique people. The summary also includes `leads`, separate `guideRequests` and `expertRequests`, `pendingExpertRequests`, `guideAccepted`, `guideDelivered`, `guideDeliveryFailures`, historical `marketingOptIns`, `kickedPlayers`, `timedOutPlayers`, `playerLeaves`, `twilioProductLinkClicksByProduct: {video,messaging,segment}`, and `githubRepoClicksBySource: {phone,spectator,arenaQr,arenaLink}`. New forms cannot create marketing opt-in. A lead row contains the saved field values and field-definition snapshot, `deliveryStatus`, `expertStatus`, and guide/expert request timestamps. The lead CSV includes those status and request-date columns. Lead rows filter on capture date; guide and expert counts filter on request timestamps. `expertQueue` contains pending expert requests regardless of date range until staff resolves them; the event activity export includes later request actions even when the lead was captured outside the range. Activity counters use the requested event/date filter. Historical GitHub clicks without a source count as `phone`. Outbound fields count clicks or scans through the redirect, not verified destination page loads or GitHub stars.

Twilio signed webhooks live at `/webhooks/twilio/messaging` and `/webhooks/twilio/video`. They validate the exact public URL and `X-Twilio-Signature`, then deduplicate message/event IDs before changing state or metrics. An SMS or WhatsApp ballot message arriving during a paused open vote receives a TwiML reply saying the vote was not counted and asking the visitor to resend after staff resume; a genuinely closed ballot gets a different reply. `POST /webhooks/sendgrid/events` receives a JSON array of SendGrid delivery events. It requires a valid `X-Twilio-Email-Event-Webhook-Signature` and timestamp verified with `SENDGRID_EVENT_WEBHOOK_PUBLIC_KEY`, deduplicates `sg_event_id`, and correlates non-PII `lsh_job_id` custom arguments with saved guide delivery jobs. Mail Send `202` records `accepted`; a signed callback can advance the lead to `processed`, `deferred`, `delivered`, `bounced`, or `dropped`. Signed callbacks can reconcile previously accepted messages while `SENDGRID_EMAIL_ENABLED=0`; that flag only pauses outbound Mail Send calls. Definite HTTP 429 send failures retry with backoff. HTTP 503 and uncertain network outcomes become `needs-review` without automatic retry to avoid a possible duplicate. Without a signed webhook, `accepted` is not proof of delivery.
